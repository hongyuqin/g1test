题目 1：MySQL事务隔离级别与锁机制

请详细解释MySQL的四种事务隔离级别（Read Uncommitted、Read Committed、Repeatable Read、Serializable），并说明每种隔离级别下可能出现的问题（脏读、不可重复读、幻读）。同时，请解释MySQL的锁机制，包括行锁、表锁、间隙锁、临键锁的区别和使用场景。

📝 参考答案

事务隔离级别：
  • Read Uncommitted：最低级别，可能读取到未提交的数据，存在脏读问题
  • Read Committed：只能读取已提交的数据，避免脏读，但存在不可重复读
  • Repeatable Read：MySQL默认级别，保证同一事务内多次读取结果一致，但存在幻读
  • Serializable：最高级别，完全串行化执行，避免所有并发问题但性能最差
锁机制详解：
  • 行锁（Record Lock）：锁定索引记录，InnoDB默认使用
  • 表锁（Table Lock）：锁定整个表，MyISAM使用
  • 间隙锁（Gap Lock）：锁定索引记录之间的间隙，防止幻读
  • 临键锁（Next-Key Lock）：行锁+间隙锁的组合
实际应用场景：

在高并发系统中，需要根据业务场景选择合适的隔离级别。例如：

  • 金融交易：使用Serializable确保数据一致性
  • 报表查询：使用Read Committed提高并发性能
  • 一般业务：使用Repeatable Read平衡性能和一致性

题目 2：Redis持久化与集群架构

请详细说明Redis的两种持久化方式（RDB和AOF）的优缺点，以及混合持久化的实现原理。同时，请解释Redis集群的三种模式（主从复制、哨兵模式、Cluster模式）的区别，以及在实际项目中如何选择合适的集群方案。

📝 参考答案

持久化方式对比：
  • RDB（快照）：
    优点：恢复速度快，文件紧凑，适合备份
    缺点：可能丢失最后一次快照后的数据，fork子进程消耗内存
  • AOF（日志）：
    优点：数据安全性高，支持多种fsync策略
    缺点：文件较大，恢复速度慢，重写过程复杂
  • 混合持久化：结合RDB和AOF，先RDB快照，再追加AOF日志
集群模式对比：
  • 主从复制：简单易用，适合读写分离，但无自动故障转移
  • 哨兵模式：自动故障检测和转移，适合中小规模集群
  • Cluster模式：分片存储，支持水平扩展，适合大规模数据
选择建议：
  • 小规模应用：主从复制 + 哨兵
  • 大规模应用：Cluster模式
  • 数据量<10GB：哨兵模式
  • 数据量>10GB：Cluster模式

题目 4：RocketMQ事务消息实现

请详细解释RocketMQ事务消息的实现原理，包括两阶段提交（2PC）的具体流程，以及如何保证分布式事务的一致性。同时，请说明RocketMQ的存储架构（CommitLog、ConsumeQueue、IndexFile）对事务消息的支持。

📝 参考答案

事务消息两阶段提交流程：
  • 第一阶段（发送半事务消息）：
    1. 生产者发送半事务消息到MQ
    2. MQ返回消息ID，但不立即投递给消费者
    3. 生产者执行本地事务
  • 第二阶段（提交或回滚）：
    1. 生产者根据本地事务结果发送提交或回滚指令
    2. MQ根据指令决定是否投递消息给消费者
一致性保证机制：
  • 事务状态回查：MQ定期回查生产者确认事务状态
  • 超时机制：超过回查次数后自动回滚
  • 幂等性：通过事务ID避免重复处理
存储架构支持：
  • CommitLog：顺序写入事务消息，保证性能
  • ConsumeQueue：记录消息的消费状态
  • 事务状态存储：单独存储事务状态信息
实际应用场景：
  • 订单支付流程：确保订单创建和支付通知的原子性
  • 库存扣减：确保库存更新和订单创建的原子性
  • 积分系统：确保积分扣减和业务操作的原子性

题目 5：分布式系统CAP理论与一致性算法

请详细解释CAP理论（一致性、可用性、分区容错性）的含义，以及在实际分布式系统设计中如何权衡这三个特性。同时，请说明Paxos、Raft等一致性算法的核心思想，以及它们在分布式系统中的具体应用。

📝 参考答案

CAP理论详解：
  • 一致性（Consistency）：所有节点在同一时间看到的数据是一致的
  • 可用性（Availability）：每个请求都能收到一个响应，但不保证是最新的
  • 分区容错性（Partition Tolerance）：系统在网络分区的情况下仍能继续工作
CAP权衡策略：
  • CP系统：优先保证一致性和分区容错性，如分布式数据库
  • AP系统：优先保证可用性和分区容错性，如NoSQL数据库
  • CA系统：优先保证一致性和可用性，如单机数据库
一致性算法对比：
  • Paxos算法：
    - 三阶段提交：Prepare、Accept、Learn
    - 复杂但理论完备，适合学术研究
    - 实际实现困难，如Google Chubby
  • Raft算法：
    - 领导者选举、日志复制、安全性
    - 易于理解和实现
    - 广泛应用：Etcd、Consul、Kubernetes
实际应用场景：
  • 分布式配置中心：使用Raft保证配置一致性
  • 分布式锁：使用Zookeeper的ZAB协议
  • 服务发现：使用Consul的Raft实现

题目 7：JVM内存模型与垃圾回收

请详细解释JVM的内存模型，包括堆内存、方法区、虚拟机栈、本地方法栈、程序计数器的作用和特点。同时，请说明不同垃圾回收器（Serial、Parallel、CMS、G1、ZGC）的工作原理和适用场景。

📝 参考答案

JVM内存模型：
  • 堆内存（Heap）：
    - 存储对象实例，分为新生代和老年代
    - 新生代：Eden、Survivor（S0、S1）
    - 老年代：长期存活的对象
  • 方法区（Metaspace）：
    - 存储类信息、常量、静态变量
    - JDK8后使用本地内存，不再受JVM限制
  • 虚拟机栈：存储局部变量、操作数栈、方法出口
  • 本地方法栈：为本地方法服务
  • 程序计数器：当前线程执行的字节码行号
垃圾回收器对比：
  • Serial GC：单线程，适合客户端应用
  • Parallel GC：多线程，适合服务器应用
  • CMS GC：并发标记清除，低延迟，适合Web应用
  • G1 GC：分代收集，可预测停顿时间
  • ZGC：低延迟，适合大内存应用
GC调优策略：
  • 内存分配：合理设置堆大小、新生代比例
  • GC频率：控制Minor GC和Major GC的频率
  • 停顿时间：选择合适的GC器减少停顿
  • 吞吐量：平衡GC时间和应用运行时间
实际应用场景：
  • 高并发Web应用：使用G1或ZGC
  • 大数据处理：使用Parallel GC
  • 实时系统：使用ZGC保证低延迟

题目 8：分布式缓存设计与缓存一致性

请详细说明分布式缓存的设计原则和架构模式，包括缓存更新策略、缓存穿透、缓存击穿、缓存雪崩的解决方案。同时，请解释如何保证分布式缓存的一致性，包括缓存与数据库的一致性协议。

📝 参考答案

缓存更新策略：
  • Cache Aside：先更新数据库，再删除缓存
  • Write Through：同时更新缓存和数据库
  • Write Behind：先更新缓存，异步更新数据库
  • Refresh Ahead：提前刷新即将过期的缓存
缓存问题解决方案：
  • 缓存穿透：
    - 布隆过滤器过滤无效key
    - 缓存空值，设置较短过期时间
    - 参数校验，拒绝无效请求
  • 缓存击穿：
    - 互斥锁防止并发重建缓存
    - 逻辑过期，异步更新缓存
    - 热点数据永不过期
  • 缓存雪崩：
    - 随机过期时间
    - 多级缓存
    - 熔断降级机制
缓存一致性保证：
  • 最终一致性：通过异步更新实现
  • 强一致性：使用分布式事务
  • 版本控制：通过版本号控制缓存更新
  • 消息队列：通过消息保证更新顺序
实际应用场景：
  • 商品详情页：使用多级缓存，CDN+Redis+本地缓存
  • 用户会话：使用Redis集群存储会话信息
  • 热点数据：使用Redis Cluster存储热点商品信息

题目 9：数据库分库分表策略与实现

请详细说明数据库分库分表的设计原则和实现方案，包括水平分片、垂直分片的区别，以及分片键的选择策略。同时，请解释分布式事务的处理方案，包括2PC、3PC、TCC、Saga等模式的特点和适用场景。

📝 参考答案

分库分表策略：
  • 水平分片：
    - 按行分割数据到不同表/库
    - 适合数据量大但表结构相同的场景
    - 分片键选择：用户ID、时间、地理位置
  • 垂直分片：
    - 按列分割数据到不同表/库
    - 适合表字段多且访问模式不同的场景
    - 分片原则：热点数据、冷数据分离
分片键选择策略：
  • 哈希分片：数据分布均匀，但无法范围查询
  • 范围分片：支持范围查询，但可能数据倾斜
  • 时间分片：适合时间序列数据
  • 复合分片：结合多个字段进行分片
分布式事务方案：
  • 2PC（两阶段提交）：
    - 准备阶段、提交阶段
    - 强一致性，但性能较差
    - 适合金融、支付等场景
  • 3PC（三阶段提交）：
    - 增加预提交阶段
    - 减少阻塞，提高性能
    - 但仍存在一致性问题
  • TCC（Try-Confirm-Cancel）：
    - 业务层面的补偿机制
    - 性能好，但开发复杂
    - 适合微服务架构
  • Saga模式：
    - 长事务的补偿机制
    - 通过事件驱动实现
    - 适合复杂业务流程
实际应用场景：
  • 电商订单：按用户ID分片，使用TCC保证一致性
  • 日志系统：按时间分片，使用Saga处理复杂流程
  • 金融交易：使用2PC保证强一致性
